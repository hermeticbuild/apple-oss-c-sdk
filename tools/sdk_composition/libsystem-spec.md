# Generating the macOS libSystem link interface

**Review draft, 19 November 2026.** This specifies a proposed implementation in this repository. Commands in the proposed CLI section are acceptance contracts for future work. Existing commands and experiments are identified separately.

## Deliverable and scope

A release for one macOS SDK version installs `usr/lib/libSystem.B.tbd` with install name `/usr/lib/libSystem.B.dylib` and a relative `usr/lib/libSystem.tbd` alias for `-lSystem`. Include the component documents needed to resolve the umbrella's reexports. Prefer one multi-document stub in the v5 JSON format with embedded libraries, subject to the linker tests below. This keeps component ownership intact and avoids making every implementation dylib a new direct-link API. Record any independently justified direct-link paths. Produce a sorted provenance manifest and a coverage report alongside the installable payload.

The first version targets **macOS SDK 26.5, arm64 and x86_64 clients**. “Complete enough” means the public libSystem interface covered by the agreed scope, including compiler, linker, macro and inline dependencies, resolves with the expected binding behavior. Enumerate every observed difference against the matching Apple reference. A consumer passing can establish demand. A lack of consumer demand alone cannot establish that a public interface is dispensable.

Count release gaps for these two client architectures. The [effective linker
comparison](../sdk_review/libsystem_review.md) tests them directly. Preserve
raw subtype evidence when qualifying a supported client, including the Apple
reference's arm64e umbrella. Mac Catalyst findings are reported outside the
release scope. There is no separate arm64e or x86_64h client qualification.

**Frameworks continue to come from Apple SDK Gen.** Pin its release and any existing framework-only repairs needed by the consumers. Separately supplied library stubs, such as the Apple system libc++ dylib stub, and the Objective-C runtime layer can be named inputs to the composed consumer SDK. The standalone libSystem output has its own manifest and digest. Generated C headers come from the existing installer. Clang resources, libc++ headers and compiler builtins belong to the toolchain. Check a provider's actual reexport relationship before classifying a difference as owned elsewhere.

This repository should contain the production recipes, pinned input specifications, publishable reviewed facts, repair workflow and repeatable qualification commands. Large upstream archives, raw runtime captures, the reference SDK and generated scratch outputs live outside Git. An offline build must be reproducible from the repository and its materialized, digest-verified public inputs. A release needing an unshareable private input cannot meet that goal.

### One official LLVM toolchain for generation

The candidate matches the existing scanner version: upstream **LLVM 23.1.2**, commit `85ac560262434c9ccfc0c183ec22d4138ed647fb`, Apple Silicon host. Verified the compressed archive SHA-256 `3da0e91b5dfe3a5ec795ad2be79b3f5e6f28c8b23edcd3847fad7742b25e0507` against the release metadata. Inspected archive entries for `clang`, `clang-installapi`, `llvm-nm`, `llvm-objdump`, `llvm-lipo`, `llvm-readtapi`, `ld64.lld`, resource headers and the macOS builtins. The packaged InstallAPI emitted both target records, an ordinary function export and a thread-local data export from a small C header, excluding its static inline function. [Official release and verification instructions](https://github.com/llvm/llvm-project/releases/tag/llvmorg-23.1.2) · [Upstream InstallAPI test](https://github.com/llvm/llvm-project/blob/llvmorg-23.1.2/clang/test/InstallAPI/functions.test)

**One host archive does not supply both target runtimes.** `llvm-lipo -info lib/clang/23/lib/darwin/libclang_rt.osx.a` reported only arm64. `llvm-nm` found `___divdc3`, `___divsc3` and `___udivti3` in that slice. Both architectures can be scanned and compiled to objects with the same host executables. For standalone link fixtures requiring x86_64 builtins, the proposed source is compiler-rt from that exact LLVM revision. Make the archive a pinned target dependency, record its production command and digest, verify its slice and genuine link behavior. Stage 0 should build builtins as a static library with the official compiler and the generated C installation, with executable try-links disabled where appropriate. Confirm the actual build has no circular dependency on the finished stub or host SDK. If blocked, report the dependency before selecting another source. The hermetic-llvm consumer tests use that consumer's own normal toolchain.

Bootstrap capability check (observed with an empty sysroot, an absolute public header path in the JSON list, and no SDK headers):

```sh
"$LLVM/bin/clang-installapi" -x c -nostdinc -isysroot "$EMPTY_ROOT" \
  -target arm64-apple-macos11 -target x86_64-apple-macos11 \
  -dynamiclib -install_name /usr/lib/libExample.dylib --filetype=tbd-v4 \
  "$WORK/headers.json" -o "$WORK/example.tbd"
```

The header list has the form `{"version":"3","headers":[{"type":"public","path":"…"}]}`. The production probe must additionally exercise the chosen v5 reader/writer and actual generated headers. Version detection for the bundle can use `clang --version` plus the executable digests. InstallAPI's usual driver flags do not make `--version` a reliable capability test.

**Recommendation for Intel builtins.** Defer building an Intel archive until a real independent fixture requires a static helper. In a reference-only experiment the official Clang emitted `___divdc3`, `___divsc3` and `___udivti3` for complex double, complex float and unsigned 128-bit division on both targets. At minimum macOS 11, official LLD linked the x86_64 fixture against SDK 26.5 with `-lSystem` alone. All three imports bound through libSystem. The equivalent arm64 link failed for the two complex helpers. Adding the bundled arm64 archive after `-lSystem` resolved those two locally and left only `___udivti3` dynamically bound. Preserve both the archive-free and archive-assisted outcomes. An extra archive can mask a missing export. A future independently needed Intel archive carries its own build, provenance and cache cost, but uses the same LLVM revision and keeps the generation toolchain independent of its consumers.

## Proposed CLI and script contracts

Use `python3 -m tools.libsystem` as the producer entry point. Keep helpers close to their data, consolidate subcommands where they share readers, and use Make for phase dependencies. The table defines operations, not a requirement to write one script per row. Python's standard library can emit deterministic TBD v5 JSON. First prove LLD and the differential reader accept the embedded component layout. A writer format change requires an explicit compatibility finding.

| Operation and caller | Inputs → outputs | Required behavior on failure |
| --- | --- | --- |
| `tools.toolchain` prepare/verify, operator or CI | Release lock, download cache → absolute LLVM directory, verified capabilities, target-runtime inventory | Validate signatures/hashes on acquisition, rehash cached inputs, test actual two-target InstallAPI output and linking fixtures. Report missing target slices separately from missing executables. Offline mode reports the exact missing input. |
| `qualify_headers` census, agent or CI | C install and manifest, pin, profiles and optional reference → one row per installed path and context, diagnostics, include trace | Run all independent cases. Distinguish umbrella, language, feature, architecture, absent dependency and semantic mismatch. ### Proposed operator invocation

These names specify interfaces to implement. Reuse `python3 -m tools.sources.locked_sources prepare --sdk macosx26.5`, `make install`, `make test`, `trace_includes` and `audit_sdk_headers` for the operations already implemented. The three review adapters below can share a single CLI. Implement each new adapter with a named caller in the package Makefile, qualification wrapper or skill.

```sh
# Existing C installation entry points after acquiring the official LLVM bundle
make install SDK=macosx26.5 CLANG="$LLVM/bin/clang" OUT="$C_INSTALL"
make test SDK=macosx26.5 CLANG="$LLVM/bin/clang" OUT="$C_INSTALL"

# Proposed offline producer; resolves the matrix, inputs and evidence from the lock
python3 -m tools.libsystem build --sdk macosx26.5 --llvm "$LLVM" \
  --c-install "$C_INSTALL" --sources "$SOURCES" --work "$WORK/build" --out "$PACKAGE"

# Proposed local qualification and drill-down; do not feed the reference report to build
python3 -m tools.sdk_review.libsystem compare-libsystem --sdk macosx26.5 \
  --reference "$APPLE_SDK" --candidate "$PACKAGE" --llvm "$LLVM" --out "$WORK/diff"
python3 -m tools.sdk_review.libsystem explain-libsystem --work "$WORK" \
  --symbol getgroups --arch x86_64 --minimum 11.0 --profile darwin
python3 -m tools.sdk_review.libsystem verify-libsystem-links --sdk macosx26.5 \
  --reference "$APPLE_SDK" --candidate "$PACKAGE" --c-install "$C_INSTALL" \
  --llvm "$LLVM" --out "$WORK/links"
```

Initial profile fixtures are default C17, Darwin extensions (`_DARWIN_C_SOURCE`), POSIX 2008 (`_POSIX_C_SOURCE=200809L`), X/Open (`_XOPEN_SOURCE=700`), and the upstream getgroups/inode compatibility selectors where defined for the client target. Preserve the existing C11 shipping fixture. Keep profile changes and applicability in versioned inputs. Derive the deployment samples from the claimed endpoints and independently observed changes, then compare each normalized configuration and record why any two matrix entries are equivalent. Run the SDK-independent compiler with explicit `-target`, `-isysroot`, `-nostdinc` and only the pinned resource and install include directories. Record assembler-with-preprocessor or Blocks contexts where justified. Generate probes by canonical declaration with a unique retained reference per candidate and map each relocation to that reference. Report unmatched or additional symbol relocations separately so implicit code generation remains visible.

## Implementation sequence and evidence required to advance

Maintain the [implementation journal](../libsystem/progress.md) from the first milestone through handoff. The person or agent doing the work updates it when a milestone advances, an experiment changes the diagnosis, a decision is requested or answered, or the work pauses. Each entry records the SDK and affected targets, finding, evidence or reproducible command, decision status and scope, and the next action or blocker. Link to the canonical fixture, recipe, decision ID or run receipt. Preserve superseded findings with a dated correction. Keep raw reference data local. The producer has no dependency on the journal.

1. **Freeze the toolchain and input contract.** Extend the existing resolver. Verify the official bundle, two-target AST/InstallAPI, linker and inspector on a synthetic header, a TLS variable, an inline function and an assembler alias. Prepare target runtimes only where link fixtures need them. Freeze source, tool, C manifest and reference identification. Repeat cold and warm resolution.
2. **Deliver the tools before running the production inventory.** Implement the commands in the CLI contracts in dependency order. First deliver lock verification, manifest/context reading and the header census. Next deliver scanning, compiler-import discovery, evidence capture/reading, provider resolution and emission. Then deliver comparison, gap enumeration and explanation, paired linking, composition checks and qualification runners. Exercise the commands from their documented entry points using small checked-in inputs. The operator README and repository-local agent skill must use those same entry points. Apply the readiness checks below before beginning the full baseline. The full consumer builds belong at the release gate.
3. **Build the header backlog before repairing headers.** Run existing `make install`, `make test`, shipping and discovery traces, the SDK path audit, semantic/ABI review and the new census on the same snapshot. Run both architectures with root-by-root and aggregate probes. Seed review with the two missing XNU machine assembler includes, the eventlink private prerequisite, three libplatform decisions and Clang's `tgmath.h`. Include all other failures and unreviewed paths. Group by cause. Save exact reproductions and a scope decision for every group. [Existing SDK audit commands](../sdk_review/README.md)
4. **Close that backlog one group at a time.** Reproduce before, find a pinned public Apple install rule or establish the intended include context, repair the owning recipe/test or record the approved omission. Rerun the original case, both target probes and the census. Newly exposed dependencies become linked child issues. Stop for Corentin when the necessary standalone C input lacks an approved source, a private dependency would have to ship, or an omission would narrow agreed scope. Proceed to broad extraction once each in-scope defect is fixed or explicitly accepted and the baseline has no forgotten rows.
5. **Generate client references.** For each architecture, language, feature profile and relevant deployment minimum, parse a translation unit including its public root under the locked compiler. Supply only Clang resource headers and the C installation. Use InstallAPI with a public-header file list for linkage eligibility. Use the same compiler's JSON AST for physical source, C names, redeclarations and typed reference generation. Match by context and Mach-O spelling, and surface disagreements. Generate retained address references for external functions/data and accessor functions for TLS. Compile actual macro/inline calls in focused checked-in fixtures. Use relocations to associate imports to references. Compile types and folded constants as layout/value tests. Keep these out of the export list unless a separate external definition is demonstrated.
6. **Build the component graph and coverage inventory.** Read Apple's pinned Libsystem component lists and link rules and relevant component export maps, assembler aliases, weak definitions and compatibility sources. Start discovery from both headers **and** these public source inventories. Include public headerless entry points and implicit compiler/linker demands. Track runtime-only and reference-only names in the local audit so the header inventory cannot silently define completeness. Verify current runtime image metadata on each observed slice. Sort public demands by graph reachability, select a defining provider and retain the umbrella through which the client binds. Resolve zero/multiple matches by evidence or review. Example: `zlib.h` may be installed, but `-lz` is a distinct direct interface.
7. **Model compatibility and emit a small vertical slice.** Start with `puts`, both `stat` spellings, the default/Darwin `getgroups` pair, a weak import, TLS fixture, `dyld_stub_binder` and complex division. Source linker directives independently from the matching component or compiler-rt source/configuration. Identify unsupported or missing behavior at every relevant deployment boundary. Preserve metadata including install names, versions, flags and forwarding. Emit one generated umbrella with the required child documents; link and run clients. Then expand to every in-scope component. The small slice proves the machinery only.
8. **Compare, investigate and regenerate.** Use the local official 26.5 SDK as the differential oracle. Preserve raw document/target labels. For example the parent reference lists `arm64e-macos`, while the embedded compiler-rt document also has `arm64-macos`. A single `llvm-readtapi -extract -arch arm64` on the whole reference fails at the parent. Use the fixture-tested per-document parser (for v4, split document boundaries and use the pinned reader per document/slice; for v5, traverse main and child objects). Include fixtures proving zero lost children, flags and target groups, including mixed macOS/Catalyst labels. Keep an independent `llvm-readtapi -compare` result and real differential links. Regenerate after each approved root-cause fix until the finish conditions hold.
9. **Qualify the exact composition and publish the reproduction instructions.** Run the fixture-tested composer with the generated libSystem layer and verify its provider receipt against the release manifest. Pin SDK Gen frameworks and any existing repairs, identifying every overlay separately. Keep toolchain C++ headers/builtins out of the SDK payload. Exercise a framework-free C client first, then the three real consumers on the same archived SDK. Record exact build/test invocations, revisions, filters, effective toolchain and archive SHA. A fresh maintainer must be able to reproduce the standalone TBD from the operator README, and investigate one open/seeded gap using the repository-local skill.

## Maintainer and agent procedure

The skill starts by asking which SDK to generate only if the invocation leaves that ambiguous. Select the applicable workflow:

- **Rebuild a reviewed SDK.** From a clean checkout and empty cache, fetch and verify the locked public inputs, run the documented offline producer, and compare its TBD, alias and manifest with the release receipt.
- **Update an existing SDK.** Preserve the previous lock and receipts. Prepare the new source and tool inputs, regenerate inventories and differences, reopen approvals whose evidence or membership changed, and work the resulting backlog. Run the release gate and record the new qualified digest.
- **Establish a first baseline.** With no prior lock, approval ledger or generated tree for the selected SDK, identify the upstream distribution, prepare a fresh version lock, and run the census and reference comparison with empty decisions. Every unresolved difference starts open. Follow the same review and qualification loop to establish the first approved inputs; the next clean build consumes those inputs unattended.

For a gap investigation, verify lock and baseline digests, regenerate the backlog and choose one unclassified cause. Consult the journal for the last verified result and pending decisions. The [escalation policy](#when-the-agent-must-ask-corentin) applies in all three workflows. When a finding changes how a future run should work, put the repeatable part into its owning command, fixture or skill instruction and link it from the journal.

1. **Reproduce** the smallest failing context with `explain-libsystem`. For a header, show the public root, feature macros, include trace and architecture. For a symbol, show the C expression or generating instruction, object relocation, install name and failing deployment range. Record whether the reference also fails.
2. **Trace ownership.** Start with the installed header's receipt and pinned public install rule. For linkage, consult public source definitions, export lists, assembler directives, Libsystem's reexport script and compiler-rt as appropriate. Runtime inspection can verify a specific provider. The reference SDK can identify a question to investigate. Keep the evidence for an answer independently attributable.
3. **Choose the repair location.** Header or context error → owning recipe or context exception. Eligibility, alias, provider or deployment error shared across rows → repair the deterministic algorithm and add the smallest regression. Legitimate component exception → add a scoped, evidenced record. External framework failure → reproduce with the pinned SDK Gen layer and track there. If a framework test exercises a missing public libSystem symbol, return that symbol to this backlog.
4. **Escalate at the decision boundary below.** Keep the affected row open, preserve its reproducer, and continue independent work while waiting for an answer.
5. **Close a row** only with a before/after reproducer or a reviewed omission with evidence. Re-run affected profiles on both architectures, recompute the full diff and compare counts. Invalidate an approval when its source, target membership or evidence changes. Keep unresolved rows visible even if all workloads pass.

### When the agent must ask Corentin

Prompt as soon as the decision becomes necessary and before changing the affected recipe, evidence record, approval or release claim. Group rows only when the same cause and proposed decision apply to all of them.

| Prompt when… | Example and decision needed |
| --- | --- |
| 1. A required standalone C input lacks an established public source or install rule | An installed public header includes a type found only in an XNU private install list. Show the upstream rule and affected clients. Ask whether to keep the gap open, investigate another source, or permit a scoped derivation. |
| 2. A fix needs a project-specific departure from Apple's rule | A proposed copy, rename, handwritten declaration, post-install edit, alias, symbol injection or consumer-specific overlay lacks a pinned upstream rule for that transformation. Ask before adding it, even if it makes a test pass. An upstream rule explicitly generating two outputs from one input is itself a faithful mapping. |
| 3. ABI or linkage evidence is ambiguous or missing | Two reachable images export a name and the client binding remains ambiguous, or a proposed weak/TLS flag, deployment boundary, layout or architecture mapping rests on inference. Show the conflicting evidence and the test that could distinguish it. Leave the row unresolved while evidence is insufficient. |
| 4. A proposed input crosses an agreed provenance or package boundary | Examples include using an Xcode or SDK Gen libSystem record as generation input, publishing a new class of runtime-derived facts, or pulling toolchain content into the SDK. Explain the intended use, alternatives and provenance implications. Existing approval covers recording a verified runtime provider for an independently established public API. |
| 5. A repair narrows public scope or changes an approval | Examples include omitting a potentially public symbol, broadening a waiver beyond its reviewed members, or dropping an architecture, profile or deployment range. Give the exact affected set and consumer impact. A documented omission already covered by the agreed policy can follow the existing review procedure. |
| 6. A workaround would weaken or bypass validation | Examples include patching a consumer, disabling a failing test, changing the reference to match the candidate, adding a static archive that conceals a missing system export, or counting a cross-build as an executed bootstrap. Report the failing gate and the work needed to satisfy it. Any changed acceptance criterion needs an explicit decision and a visible change to the release claim. |
| 7. The correction requires a material change outside this deliverable | A diagnosis may identify an SDK Gen framework defect or a hermetic-llvm toolchain defect. Use the existing authorized framework composition and capture an isolated reproducer. Ask before substituting another provider or expanding this work into a separate upstream implementation. |

**Proceed autonomously** with read-only investigation, isolated diagnostic overlays, a faithful port of a pinned public install/generation rule, and general tool defects demonstrated by a failing fixture. Label a diagnostic overlay as scratch evidence and keep it outside release inputs. Also proceed with previously approved exceptions within their recorded scope. For example, installing the two machine assembler headers by XNU's own generated-install rules is ordinary recipe work. Handwriting their contents to make the includes pass triggers case 2.

**Each prompt should contain** the gap ID and affected paths/symbols, target and deployment range, smallest reproducer, observed versus expected result, upstream evidence already checked, and the precise departure being proposed. Give a recommendation and alternatives, including the effect of leaving the gap open. Record the answer with its scope and reopening condition. Approval of an experiment permits the experiment; closure still requires the specified evidence or an explicitly accepted omission.

## Validation loop and finish gate

After running the consumer workloads and before release sign-off, reconcile
every divergent installed C header against the exact candidate's
`compare_c_interfaces` report. The 26.5 baseline had 45 differing paths;
the current comparison has 48. Retain per-path decisions for the entire set.
When one path contains multiple independent differences, decide each
separately. A passing compiler bootstrap is evidence only for the paths
and behavior it exercised.

For each difference, record the affected arm64 or x86_64 macOS client, the
behavior at risk, its source receipt and one of these outcomes:

- **Fixed and verified** with the before/after probe or artifact.
- **Accepted difference** with its rationale and scope, plus any required
  maintainer approval. For a text-only difference, record the comparison
  that establishes that the declarations agree.
- **Open** with a reproducer or a specific evidence gap and its release impact.

Reuse the first audit's findings. Prioritize target and availability branches,
ABI layout and calling convention, public declarations, and the names or
weakness of linker imports. New, changed or disappeared differences reopen
the affected decisions. An unexplained potentially public ABI difference
blocks release. No release criterion requires matching header bytes.
